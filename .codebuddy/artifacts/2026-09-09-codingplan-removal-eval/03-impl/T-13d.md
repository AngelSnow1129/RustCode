# T-13d 收口 `codingplan_models_are_read_only_in_the_panel` 红测试

## 1. 性质判断：删除（不是误伤）

失败点 `provider_panel.rs:3550`：

```
assertion failed: ProviderPanel::managed_account(&cfg, "official-alias")
```

根因链：

- `ProviderPanel::managed_account` → `Config::account_is_codingplan_managed`
  （`crates/rustcode-config/src/config/mod.rs:820`）
- 该函数对**非** `RustCode*` 前缀账号的唯一判据是
  `endpoints::is_codingplan_llm_gateway(base_url)`
  （`crates/rustcode-config/src/endpoints.rs:204`）
- `HOSTED_CODINGPLAN_LLM_BASE_URL = ""`（`endpoints.rs:79`），函数注释明确写
  “no host is treated as a gateway by default / 平台中立”。因此
  `is_codingplan_llm_gateway("https://gateway.test.example/v1")` 恒为 `false`。

结论：该用例断言的正是**已被移除的 codingplan 行为**——
「base_url 指向 codingplan 网关的别名账号（`official-alias`）及其模型在面板中
是只读/受管的（`managed_account` / `managed_model` / `can_add_model` /
`has_add_row` 全为受管语义）」。codingplan 移除后不存在任何默认网关主机，
该语义已不成立。按任务口径 → **连同用例一起删**，未改任何断言去凑绿。

旁证：`RustCode` 那条断言仍为 true，仅因 `is_codingplan_provider_name("RustCode")`
走硬编码前缀名，与用例要测的「网关别名账号受管」不是同一条路径。
