Login Methods

RustCode is bring-your-own-key (BYO) by default: point it at any third-party LLM provider with an API key and you are done — no account, no login. Some distributions additionally ship an optional managed sign-in (/login) that authorizes a managed endpoint and can auto-provision provider and model settings. This page covers both paths.

Two paths at a glance

PathCommandWho it's for
API key (default)/provider or hand-edit configEveryone on the open build — use your own OpenAI / Claude / DeepSeek key, or a local Ollama endpoint. No account needed.
Managed sign-in (optional)/loginOnly present in distributions that ship managed-gateway support — a browser/device flow that authorizes your distribution's managed endpoint, can claim quota, and auto-configures providers.

The open build includes no managed gateway and no account system. If /login is unavailable or reports an error in your build, that is expected — use the API key path below. Any managed sign-in, free quota, or tier system is defined by your distribution, not by RustCode itself.

API key method (default, BYO)

To use your own OpenAI / Claude / DeepSeek / GLM key, there are three ways:

Option A: /provider in the TUI

  1. Type /provider in the TUI.
  2. Choose a third-party provider preset or a custom endpoint, enter its API key, then add one or more models under that account.
  3. The configuration is written back to ~/.rustcode/config.toml.

Option B: hand-edit the config file

Edit ~/.rustcode/config.toml directly and add a [providers.*] entry; see ProviderConfig fields.

Option C: one-shot CLI override

Don't want to touch the config file and only need a different provider for one run? Add flags at launch:

rustcode --provider deepseek --model deepseek-reasoner

Running fully offline? Configure a local Ollama provider — no key and no login required.

Managed sign-in (optional, distribution-provided)

Some RustCode distributions ship a managed endpoint: a hosted gateway with its own account system, quota, and model list. In those builds /login runs a browser/device authorization against your distribution's authorization page — RustCode itself has no compiled-in account host. After authorizing, the build claims whatever quota your distribution grants and writes a provider config automatically; re-running /login idempotently re-syncs the entitled model list.

Entitlements, free tiers, and quota windows are set by the distribution — check your distributor's documentation for what is included and how to claim it.

From the first-run wizard

  1. The first time you run rustcode, the 3-step wizard pops up automatically.
  2. Step 1 (welcome): press Enter. Step 2 (language): press 1 / 2 / 3 to pick.
  3. Step 3 (setup): if your distribution offers managed sign-in, pick that option; otherwise choose manual configuration (API key) or skip.
  4. The browser opens your distribution's authorization page — click Allow.
  5. After authorization, the TUI writes the provider config. No need to touch config.toml — start sending messages.

If you skipped earlier and want to redo the wizard, run /welcome any time.

From an existing session

Once inside the TUI, run:

/login

The browser opens to complete authorization and refresh the provider list. Running it again re-syncs the model list — the local managed providers are updated to the latest entitled models. Requires a build with managed-gateway support.

From the command line

rustcode login

Useful in scripts, remote servers, or container images for a one-shot setup. The CLI subcommand and the TUI /login share the same flow and emit the same report. In builds without managed-gateway support this command is unavailable — use the config file or environment variables instead.

Check status / log out

rustcode status     # or /status in the TUI — includes managed-endpoint usage and expiry
rustcode logout     # or /logout in the TUI — clears the OAuth token

Which one should I pick?

  • Open build / first-time user → API key (/provider or hand-edit config) — bring your own key; no account needed.
  • Your distribution ships a managed gateway → managed sign-in (/login) is the lowest-friction path; it only exists in those builds.
  • Running in CI / scripts → API key via config file or env vars.
  • Fully offline → configure an Ollama provider — no login required.
